## 1. Запрос

```
Я выполняю вариант 13 лабораторной по процедурной декомпозиции на C17.
Цель моей программы: проверить возможность аренды автомобиля и рассчитать её стоимость.
Входы: days; distance, км; category (1–3); age; experience, лет; missing_fuel, л; insurance (0/1). Ввод — одним scanf, 7 значений одной строкой.
Формулы: daily_rate 1→70, 2→110, 3→180 BYN; base = days·daily_rate + distance·0,25; young_fee = 0,15·base при age < 25; fuel_fee = missing_fuel·2,2; insurance_fee = 18·days·insurance; total = base + young_fee + fuel_fee + insurance_fee.
Статус: DENIED, если age < 21 или experience < 1; иначе HIGH_DEPOSIT, если category = 3 и insurance = 0; иначе FUEL_CHARGE, если missing_fuel > 0; иначе ACCEPTED.
Ограничения технического задания: без массивов, структур, глобальных изменяемых переменных, динамической памяти; минимум 5 функций кроме main.

Мой проект функций и контракты:
| Функция | Ответственность | Параметры и допустимые значения | Результат | Побочные эффекты |
| get_daily_rate | Возвращает суточный тариф по категории. | category ∈ {1,2,3} | double: 70/110/180; 0 для недопустимой категории | нет |
| calc_base | Базовая стоимость по дням и пробегу. | days ≥ 1; daily_rate > 0; distance ≥ 0 | double | нет |
| calc_young_fee | Надбавка для водителя младше 25. | age ≥ 16; base ≥ 0 | double: 0,15·base при age < 25, иначе 0 | нет |
| calc_fuel_fee | Плата за недостающее топливо. | 0 ≤ missing_fuel ≤ 100 | double | нет |
| calc_insurance_fee | Плата за страховку за весь срок. | days ≥ 1; insurance ∈ {0,1} | double | нет |
| get_status | Итоговый статус по приоритету правил. | значения, уже прошедшие проверку | int: 0 DENIED, 1 HIGH_DEPOSIT, 2 FUEL_CHARGE, 3 ACCEPTED | нет |
| is_input_valid | Проверяет диапазоны всех входов (days 1..365, distance 0..100000, category 1..3, age 16..100, experience 0..age−16, missing_fuel 0..100, insurance 0/1). | значения после успешного scanf | int: 1 корректно, 0 нет | печатает сообщение о первой ошибке |
| print_status | Печатает название статуса по коду. | status ∈ {0..3} | void | вывод |
| print_report | Печатает все суммы и статус. | суммы ≥ 0; status ∈ {0..3} | void | вывод |
| print_age_scenario | Пересчитывает надбавку, итог и статус для другого возраста и печатает строку. | scenario_age + остальные готовые величины | void | вывод |
| main | Сценарий: ввод → проверка → расчёт (total = сумма частей прямо в main) → отчёт → сценарии по возрасту → самопроверка PASS/FAIL → мутационный тест. | — | 0 успех, 1 ошибка ввода | ввод, вывод |
Дополнительно: суммы и статус выводятся даже при статусе DENIED.

Проверь границы ответственности, параметры и возвращаемые значения.
Не предлагай готовый код и не переписывай решение. Для каждого замечания предложи тест, которым его можно подтвердить или опровергнуть.
```

## 2. Ответ AI (полностью)

> В целом декомпозиция хорошая. Расчёт разбит на чистые функции, вывод вынесен отдельно, функций больше пяти. Ниже замечания: сначала существенные, потом мелкие. К каждому есть тест, который его подтвердит или опровергнет.
>
> **Существенные**
>
> **1. `print_age_scenario` и считает, и печатает. Формула `total` записана в двух местах.** Функция заново считает надбавку, итог и статус, то есть повторяет логику `main`. При этом `total` в `main` считается прямо в коде, отдельной функции для него нет. Получается, что формула итога записана дважды. Если исправить одно место, второе может остаться прежним, и мутационный тест поймает расхождение только в одном из них. Параметров тоже много: возраст сценария, `base`, `fuel_fee`, `insurance_fee`, `experience`, `category`, `insurance`, `missing_fuel`. Это около восьми.
> *Тест (согласованность):* задайте возраст сценария равным введённому возрасту. Итог и статус в строке сценария должны совпасть с основным отчётом до копейки.
> *Тест (мутация):* в `main` замените в формуле итога `+ insurance_fee` на `+ 0`. Если отчёт изменился, а строки сценариев остались прежними, логика продублирована.
>
> **2. Сценарий может получить недопустимое сочетание возраста и стажа.** `is_input_valid` требует `experience ≤ age − 16`, а `print_age_scenario` подставляет другой возраст без такой проверки. Кроме того, у `calc_young_fee` есть предусловие `age ≥ 16`.
> *Тест:* ввод `5 300 2 40 20 0 1`, сценарии с возрастом 20 и 24. При стаже 20 лет возраст 20 невозможен. Посмотрите, что напечатается: строка без пометки, пропуск или предупреждение. Поведение для такого случая нужно описать в контракте.
>
> **3. Предусловие «после успешного scanf» в `main` не проверяется.** В контракте `is_input_valid` написано «после успешного scanf», но в сценарии `main` нет шага, который проверяет, что `scanf` вернул 7. Если значений меньше, переменные останутся неинициализированными.
> *Тест 1:* ввод `5 300 2` и Ctrl+D (EOF). Ожидается код возврата 1 и никаких расчётов.
> *Тест 2:* ввод `abc`. Ожидается то же самое.
> *Тест 3:* ввод `2.5 100 1 30 5 0 0`. Если `days` читается через `%d`, `scanf` возьмёт 2, а `.5` уйдёт в `distance`. В итоге все значения сдвинутся, а `scanf` всё равно вернёт 7. Проверьте, что программа это заметит, или явно опишите такое поведение.
>
> **4. `is_input_valid` и проверяет, и печатает.** Из-за побочного вывода функцию неудобно вызывать в самопроверке: она будет печатать сообщения. Есть и вторая проблема. Ограничение на стаж зависит от возраста, поэтому порядок проверок влияет на текст ошибки.
> *Тест (порядок):* ввод `5 300 2 10 5 0 0`. Сообщение должно касаться возраста, а не стажа.
> *Тест (тихий вызов):* в самопроверке вызовите функцию на заведомо неверных данных. Если в выводе появилось сообщение об ошибке, хотя пользователь ничего не вводил, побочный эффект мешает. Одно из решений: функция возвращает код ошибки, а печатает отдельная функция.
>
> **5. `main` отвечает за слишком многое, и код возврата не описан.** Сейчас в `main` семь этапов: ввод, проверка, расчёт, отчёт, сценарии, самопроверка и мутационный тест. В контракте есть код 1 только для ошибки ввода. Какой код вернётся, если самопроверка дала FAIL, не сказано.
> *Тест:* временно испортите `calc_young_fee` (0,15 → 0,10) и посмотрите, какой код вернёт программа (`echo $?`). Если 0, провал самопроверки снаружи не виден.
>
> **6. Самопроверка может сравнивать функцию саму с собой.** Если ожидаемое значение в самопроверке получено вызовом тех же функций, проверка ничего не проверяет. Ожидаемые значения нужно посчитать вручную и записать константами.
> *Тест:* та же мутация 0,15 → 0,10. Самопроверка обязана показать FAIL. Если она пишет PASS, эталон вычисляется теми же функциями.
>
> **7. Сравнение `double` через `==`.** `0.15` в двоичном виде не представляется точно, поэтому `210 * 0.15` может дать `31.499999…`.
> *Тест:* самопроверка на входе `3 0 1 24 3 0 0`: base = 210, young_fee = 31,5. Сравните результат с `31.5` через `==` и через допуск (например, `1e-9`). Если результаты сравнений разные, нужен допуск.
>
> **Средние**
>
> **8. `get_daily_rate` возвращает 0, но этот ноль никто не обрабатывает.** Возврат 0 для недопустимой категории противоречит предусловию `calc_base` (`daily_rate > 0`). Сейчас это не проявляется только потому, что проверка ввода идёт раньше. Определитесь, что это: защитный сентинел, который вызывающий проверяет, или просто предусловие `category ∈ {1,2,3}`.
> *Тест:* `get_daily_rate(0)`, `get_daily_rate(4)` и `get_daily_rate(-1)` должны вернуть 0. Затем ввод `5 300 4 30 5 0 0`: программа должна выйти с кодом 1 до вызова `get_daily_rate`.
>
> **9. У `get_status` не указаны параметры.** Формулировка «значения, уже прошедшие проверку» не задаёт список. Функции нужны только `age`, `experience`, `category`, `insurance` и `missing_fuel`. Параметры `days` и `distance` ей не нужны.
> *Тесты на приоритет правил (age, exp, cat, ins, fuel → ожидается):* 20, 3, 3, 0, 5 → 0 DENIED; 21, 1, 3, 0, 5 → 1 HIGH_DEPOSIT; 30, 0, 1, 1, 0 → 0 DENIED; 30, 5, 3, 1, 5 → 2 FUEL_CHARGE; 30, 5, 3, 0, 0 → 1 HIGH_DEPOSIT; 30, 5, 2, 0, 0 → 3 ACCEPTED.
>
> **10. Типы входов не указаны.** Для `missing_fuel`, `distance` и `experience` нужно явно выбрать `int` или `double`. От этого зависят формат `scanf` и поведение на границах.
> *Тест:* при `missing_fuel = 0.01` должен получиться FUEL_CHARGE, если тип `double`. Если тип `int`, ввод не должен разбираться молча.
>
> **11. `print_status` при недопустимом коде.** Не описано, что печатается при `status ∉ {0..3}`.
> *Тест:* `print_status(7)`. Ожидается явное `UNKNOWN`, а не пустая строка.
>
> **Мелкие**
>
> **12. Предусловие `calc_fuel_fee` пришло из проверки ввода.** Ограничение `≤ 100` относится к проверке ввода, а не к формуле. Для самой функции достаточно `missing_fuel ≥ 0`.
> *Тест:* `calc_fuel_fee(150)` = 330. Функция работает правильно, значит верхняя граница в её контракте лишняя.
>
> **13. Граничные тесты для чистых функций:** `calc_young_fee(24, 100)` = 15, `calc_young_fee(25, 100)` = 0; `calc_base(1, 70, 0)` = 70, `calc_base(1, 70, 100000)` = 25070; `calc_insurance_fee(3, 1)` = 54, `calc_insurance_fee(3, 0)` = 0; проверка ввода на границах: `days` 0/1/365/366, `age` 15/16/100/101, `experience` = `age − 16` (проходит) и `age − 15` (не проходит).
>
> **14. Числа 0–3 вместо имён статусов.** Перечисления (`enum`) и `#define` не запрещены: это не массивы, не структуры и не изменяемые глобальные переменные.
> *Тест:* поищите в коде сравнения вида `status == 2`. Каждое такое место может разойтись с `get_status`, если порядок кодов поменяется.
>
> **15. DENIED с выводом сумм.** Решение выводить суммы при DENIED нормальное, но укажите его в контракте `print_report`, чтобы это не выглядело ошибкой.
> *Тест:* ввод `3 100 1 18 1 0 0`. Должны напечататься все суммы, включая young_fee = 0,15·base, и статус DENIED.
